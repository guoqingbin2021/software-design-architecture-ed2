ADR 001 单体事务与学生后教学班锁

> 历史证据位置：本文件记载的evidence路径指原始测试记录.zip内部的相对路径，统一见配套资源包的04_测试与验收。重新执行自检时，当前结果写入工程根目录evidence。

状态：采用。

问题：不同学生会争一个名额，同一学生还会并发选择两个冲突班。只保护教学班会漏掉学生维度的跨班规则，应用进程内锁不能协调多实例。

备选：①只有教学班悲观锁，不能排除跨班课表冲突；②乐观版本，冲突后需在新事务重读并重做全部规则；③统一取得学生锁后取得教学班锁，在READ_COMMITTED事务内查询、检查、写记录和计数。

决定：采用③。选、退及成绩写入均遵守学生→教学班顺序。课程、学分、班级时间在开放后固定；MeetingSlot本章仅一个固定周时段。远程通知不进入持锁事务。

收益：两个竞争维度均被保护，所有本地变更可共同回滚，规则容易复核。

代价：同一学生写操作串行，热门班有锁等待；死锁/超时不是满额错误，重试须建立新事务并重做检查。未经负载测试不声称吞吐量保证。

证据：backend/evidence/green中容量竞争、同学生冲突、成绩退课并发与回滚测试；新连接SQL对比计数和ACTIVE数。关联R02/R03/R06、C01/C02/C05/C06。

ADR 002 历史行与独立请求快照

状态：采用。

问题：原教材片段复用同一选课行，依当前ACTIVE关系判断重复请求；发生选课→退课→旧请求重试时，当前状态无法代表那次操作是否成功。

备选：①直接重新激活旧行，会混淆历史与新意图；②每次插历史行并用包含状态的普通唯一键，重复退课历史可能冲突；③保留历史行，生成列只约束ACTIVE，独立请求表保存成功响应。

决定：采用③。退课旧行WITHDRAWN，再选新行；学生+幂等键唯一并校验目标。请求快照与选课、计数同事务。旧键返回同一快照，即便其关联已经退课，也不创建新选课；新意图必须换键。

收益：保留审计，可处理响应丢失、并发重复和旧请求重放。

代价：增加请求存储和快照维护，客户端须理解“操作结果”与“当前课表”不同；本例无过期清理政策，正式系统需另订保留期限。

证据：旧键退后重放、同键双并发、新键重复有效关系、同键不同目标409、回滚请求表全部撤销。关联R02/R03、C03/C04/C06。

本次实际后端问题：时间窗口偏移

这是本工程开发中实际出现的缺陷。R02选课和R03退课共用教学班的选退课窗口，属于C06“原子性及边界”；截止后旧幂等请求的处理同时关联C04“请求幂等”。窗口规定为UTC绝对时刻的左闭右开区间 [open_at, close_at)：开放时刻允许，截止时刻拒绝；CLOSED状态仍禁止新的选退课。

失败现象与定位

2026-10-31的真实MySQL测试将班3的 open_at 写成 2026-10-31 10:00:00，close_at 写成 12:00:00，二者均按UTC解释。测试通过仅在 src/test 中定义的MutableClock，把当前时间固定到 10:00:00Z。开放时刻的选课却未成功。随后增加直接检查JPA加载值的断言，得到：

[Extracted: openAt]
expected: 2026-10-31T10:00 (java.time.LocalDateTime)
 but was: 2026-10-31T18:00 (java.time.LocalDateTime)
Tests run: 1, Failures: 1, Errors: 0
BUILD FAILURE

原始记录是 09-window-timezone-diagnosis.log。该断言把问题定位到数据库值与实体时间值之间：SQL中的10:00被实体读成18:00，差8小时。在本机JVM默认Asia/Shanghai、连接URL含 serverTimezone=Asia/Shanghai、Hibernate配置 hibernate.jdbc.time_zone=UTC 的组合下，用不携带时区的LocalDateTime表示窗口的绝对时刻，经过JPA/JDBC时间转换后产生了这一偏移。服务用UTC Clock取得的10:00与加载成18:00的开放时间比较，错误地判定“尚未开始”。

修改前后代码

以下是本次修复前代码的摘录，省略注解以外的实体字段和其他业务检查。时间窗实现当时已经注入Clock，但比较值与持久化值使用LocalDateTime。

// TeachingClass：修复前的实际字段与边界判断
@Column(name="open_at", nullable=false)
private LocalDateTime openAt;
@Column(name="close_at", nullable=false)
private LocalDateTime closeAt;

public void ensureSelectionWindow(LocalDateTime now) {
    ensureOpen();
    if (now.isBefore(openAt))
        throw new BusinessConflict("WINDOW_NOT_OPEN", "选退课时间尚未开始");
    if (!now.isBefore(closeAt))
        throw new BusinessConflict("WINDOW_CLOSED", "选退课时间已经截止");
}

// EnrollmentService：取得锁后检查
var now = LocalDateTime.now(clock);
target.ensureSelectionWindow(now);

修复将窗口和审计时间统一为Instant，服务从同一个可注入Clock取得绝对时刻。生产Clock由 service/TimeConfiguration.java 提供：

@Bean
public Clock clock() { return Clock.systemUTC(); }

domain/TeachingClass.java 的当前实现摘录如下；比较条件保留原定的左闭右开语义。

@Column(name="open_at", nullable=false)

service/EnrollmentService.java 中的选课顺序如下，属于等价控制流摘录；省略了幂等键格式、学生状态和其他选课规则的检查。

var student = students.lockById(actor.personId()).orElseThrow(ApiFailure::notFound);

// 完整规则通过后，Enrollment.create(student, target, now)、人数与请求快照同事务提交

服务在取得锁后取时间，避免把排队等待前的时间用作新操作的窗口依据。旧键先回放原成功快照，所以原操作在窗口内成功后，即使重试到达时已经截止，也不会被当作一次新的选课。

退课同样先锁学生、再锁教学班，再调用 enrollment.withdraw(clock.instant())。domain/Enrollment.java 先对已经WITHDRAWN的记录直接返回，再拒绝已评分记录，随后执行 teachingClass.ensureSelectionWindow(now)、释放名额并记录退课时间。这样，有效选课仍受时间窗约束，重复退课可以保持204。

Enrollment.enrolledAt、Enrollment.withdrawnAt 和 EnrollmentRequest.createdAt 也改为Instant，使用注入Clock给出的时间。V5迁移中的窗口列仍为MySQL DATETIME(6)，工程明确约定存UTC，并以 CHECK (open_at < close_at) 保护窗口定义；Hibernate继续使用UTC配置。

收益与代价

本次实际前端缺陷与修复

关联需求：R02 选课、R03 退课、C04 请求幂等。本节记录的是本轮前端开发中实际出现、由回归测试复现并修复的问题。旧片段来自修复前的 frontend/src/store.js，不是为说明问题而虚构的反例；以下只省略同一函数中无关的状态设置与异常分支。

真实触发条件：第一次选课已在服务端提交，但客户端没有收到响应；该选课随后被退掉。客户端沿用原幂等键重试时，后端正确回放第一次成功的 ACTIVE 响应快照，当前 GET /api/enrollments/me 却已无此教学班。快照证明原请求曾成功，不能证明当前仍处于已选状态。

修复前，sendEnrollment() 的实际成功分支为：

await api.enroll(target.teachingClassId, target.key);
if (startEpoch !== epoch) return;
confirmEnrollmentSuccess('选课成功。', username);
await Promise.all([loadClasses(), loadMyEnrollments()]);

这里确实已经刷新个人记录，但没有使用 GET 的返回值修正提示。因此即使刷新后的有效记录为空，“选课成功。”仍保留在页面上；后端没有复活历史，前端却把历史成功误报成当前成功。

修复后，在提交前固定 const submittedKey = target.key，成功分支的实际片段为：

await api.enroll(target.teachingClassId, target.key);
if (startEpoch !== epoch) return;
confirmEnrollmentSuccess('选课请求已处理，正在查询当前记录。', username);
const [, rows] = await Promise.all([loadClasses(), loadMyEnrollments()]);
if (startEpoch !== epoch || target.key !== submittedKey) return;
// An idempotency replay is the original success snapshot, not current enrollment state.
target.message = rows == null ? '选课请求已处理，请刷新个人记录查看当前状态。'
  : rows.some((row) => row.teachingClassId === target.teachingClassId && active(row)) ? '选课成功。'
  : '选课请求已处理，但当前有效记录中未包含此教学班；请核对当前选课。';

active(row) 在实际实现中判断 row.status === 'ACTIVE'。confirmed 表示提交请求已有明确处理结果；当前是否已选由随后读取的有效记录决定。GET 失败时不把它当成提交失败，不新建幂等键，也不自动发送新的 POST；登录代次与原请求号检查防止迟到的查询覆盖后续操作。

回归用例为 frontend/tests/store.test.js 中的“旧键回放历史成功但当前已退课时，页面不宣称当前选课成功”。测试注入返回 {id:7,teachingClassId:1,status:'ACTIVE',score:null} 的选课 API，以及返回空数组的个人记录 API，复现“历史成功快照与当前状态不同”的控制流；这是一项前端状态回归测试，不把它冒充成浏览器跨标签页实测。断言提交状态仍为 confirmed，提示包含“当前有效记录中未包含”，且不包含“选课成功”。
